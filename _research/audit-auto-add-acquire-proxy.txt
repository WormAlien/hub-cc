Point 3 — verdict

No patch is needed inside aikeysapi/auto-add.js or rumeng/auto-add.js solely to change acquireProxyFor's candidate limit: the current limit is deliberate and bounded at 3 total candidate checks, with no reuse and a 5-minute empty-pool wait. A future change should make the constant explicit (e.g. `PROXY_CANDIDATE_ATTEMPTS = 3`) and test it, but do not increase it silently: each check can include a preflight timeout and registration is already paid by the mailbox.

Changes are needed for reliable stop semantics, but in routing/transparent-proxy.js rather than these two target files. Both parent stop handlers swallow taskkill failure and return `stopped:true` immediately. Recommended safe patch: set a stop-requested state, invoke `execFileAsync('taskkill.exe', ['/PID', String(pid), '/T', '/F'])` without a swallowing catch, and return an error/non-success response when taskkill fails. Then wait briefly for the child `exit` event (bounded timeout) before reporting stopped. Keep the existing process-tree kill for Windows and SIGTERM path for non-Windows. Do not add a new direct-network fallback in acquireProxyFor.

Changes are also recommended for persistence if concurrent dashboard/refresh writers are in scope. `poolAppend` and `poolPatch` are read-modify-write temp+rename but have no interprocess lock; two writers can both read the same old pool and the later rename can erase the earlier account/patch. Safe patch: serialize writes per provider (or use a shared lock helper used by poolAppend and poolPatch), reload under the lock, apply the merge/patch, write a uniquely named temp file, rename, then release. Preserve duplicate-by-api_key behavior. A retry-on-rename is not enough to prevent lost updates.

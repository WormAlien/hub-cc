poolAppend(records) (ak:275-286, rm:366-377):
  1. disk = poolLoad()
  2. haveKeys = Set(disk.map(s=>s.api_key).filter(Boolean))
  3. fresh = records.filter(r => !haveKeys.has(r.api_key))     ← ДЕДУП ПО api_key
  4. if (!fresh.length) return 0
  5. mkdirSync(dir,{recursive:true})
  6. tmp = dir/.<name>-sessions.<pid>.tmp
  7. writeFileSync(tmp, JSON.stringify(disk.concat(fresh), null, 2) + '\n', 'utf8')
  8. renameSync(tmp, POOL_FILE)
  9. return fresh.length        ← 0 означает «дубль», это печатает лог

poolPatch(apiKey, patch) (ak:288-296, rm:379-387):
  1. disk = poolLoad()
  2. i = disk.findIndex(s => s.api_key === apiKey)
  3. i < 0 → throw new Error('сохранённый аккаунт не найден')
  4. disk[i] = { ...disk[i], ...patch }        ← shallow merge
  5. tmp = dir/.<name>-sessions.<pid>.tmp ; writeFileSync ; renameSync
  (возврата нет, undefined)

Механизм = read-modify-write + temp-файл + rename. Атомарность ЕСТЬ у самой
подмены файла (rename), межпроцессной ВЗАИМОИСКЛЮЧАЮЩЕЙ СЕКЦИИ НЕТ.
Имя tmp содержит только pid — два процесса не столкнутся на tmp, но и не узнают
друг о друге.

Дыра (lost update): A читает пул (N записей) → B читает тот же пул (N) →
A rename (N+1, свой аккаунт) → B rename (N+1, свой аккаунт, БЕЗ аккаунта A).
Аккаунт A исчез с диска, при этом poolAppend вернул A единицу и лог сказал
«✓ записан в пул». Rename атомарен, но атомарность подмены не защищает от того,
что снимок в памяти B устарел ещё до записи.
